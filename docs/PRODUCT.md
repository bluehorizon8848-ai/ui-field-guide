# UI Field Guide — 产品文档

## 一句话

给 AI 独立开发者的 UI / UX 可视化词典。**看到 → 理解 → 知道名字 → 知道什么时候用 → 学会如何告诉 AI。**

## 要解决的问题

独立开发者用 AI 写 UI，卡点几乎从不是「不会写」，而是**词不对**：

| 真实困境 | 表现 |
| --- | --- |
| 不知道叫什么 | 「我想要那个从下面弹出来的」——描述得出效果，搜不到术语 |
| 知道名字但不知道用哪个 | Toast 还是 Snackbar？Modal 还是 Bottom Sheet？问 AI 得到的答案每次都不一样 |
| 知道用哪个但说不清需求 | 「给我做个弹窗」——AI 给你一个丑的、错的、或者过度设计的 |
| 抄了别人的设计看不懂 | 收藏夹里一堆「好看的 UI 截图」，一个都说不出是什么 |

传统解法都不够：
- **设计文档站**（Material Design 等）——术语准确，但默认你已经有设计语言能力
- **组件库文档**——讲 API，不讲什么时候**不该**用
- **Figma 社区**——只有图，没有名字

## 目标用户

**主：AI 独立开发者 / Vibe Coder。** 用 AI 生成代码，产品逻辑清楚，视觉和交互术语空白。

**次：跨职能产品经理、刚接手前端的创业者。** 需要快速建立共同语言，好跟设计师和工程师对话。

**不是：** 专业 UX 设计师（他们不需要）、前端框架新手（他们要的是 API 文档）。

## 三条内容原则

### 1. Example First
先看和玩 Demo，再理解定义。每个词条的**第一个元素**就是能点的 Demo，不是定义。

理由：独立开发者的判断力是「见过的次数」，不是「读过的字数」。

### 2. Plain Language First
先说人话，再给专业术语。

```
❌ Toast 是一种轻量级的非模态瞬时反馈机制。
✅ 发完消息后屏幕角落飘出来的「已发送」，几秒自己消失。
   —— 这个叫 Toast（轻提示）。
```

### 3. AI Translation
这是本产品和所有词典的**根本区别**。每个词条都要教用户**如何准确告诉 AI**。

三层递进：
- **Level 1** 你平时怎么说话（口语）
- **Level 2** 加准确的限定（术语 + 约束）
- **Level 3** 实现级（ARIA、焦点管理、动效参数、尺寸）

外加 **Bad Prompt → Better Prompt** 对比：同一个需求怎么问才有好结果。

## 用户路径

### 路径 A：知道自己要什么（最高频）

```
首页搜索「底下弹出来」→ 命中 Bottom Sheet / Action Sheet / Drawer
→ 看 Demo → 看「什么时候不要用」
→ 复制 Level 2 Prompt → 去问 AI
```

### 路径 B：不知道叫什么（次高频）

```
首页点「我不知道它叫什么」
→ 回答两个问题（出现在哪儿 / 主要干什么）
→ 得到 3-6 个候选，每个带 SVG 示意图
→ 认出一个 → 进详情页
```

### 路径 C：知道但拿不定主意

```
首页「它们到底有什么区别」→ Toast vs Snackbar vs Alert
→ 对比表 + 三个真实 Demo 并排
→ 决策规则：「如果需要用户点一下，就不是 Toast」
→ 一句话结论
```

### 路径 D：系统学习（低频但留存强）

```
/learn → Level 1 每天都会看到的 12 个
→ 勾选，进度存本机
→ Level 2 开始真正设计 App
→ Level 3 理解 UX Pattern
```

## 页面职责

| 路由 | 职责 | 判断标准 |
| --- | --- | --- |
| `/` | 学习入口 | 5 秒内看到真实组件，不是营销 Hero |
| `/explore` | 图鉴 | 能按分类 / 难度 / 关键词收敛 |
| `/patterns/[slug]` | 词条详情 | 复制 Prompt 不超过一次点击 |
| `/compare/[slug]` | 对比详情 | 看完能做决策，不只是「哦有区别」 |
| `/learn` | 三级路径 | 随时可中断，进度不丢 |
| `/identify` | 名称探索 | 两个问题出结果，无 AI 调用 |
| `/search` | 模糊搜索 | 中文口语能搜到 |

## 内容规模（DoD）

- ≥ 30 个 Pattern → **实际 63 个**
- ≥ 15 个完整交互 Demo → **实际 60+**
- 8 组对比 → **实际 8 组**
- 每个词条独立 URL + metadata → 全部 SSG

## 视觉方向

**Editorial / Visual Dictionary / Modern / Clean / Learning-first / Card-based / Calm / Precise**

- 浅色暖灰底（`#FAF9F6`），白卡片，黑灰正文
- 8 个分类色，只用于小圆点和标签，不做大面积色块
- 衬线感排版节奏，紧字距标题，大留白

**明确避免：**
- ❌ 企业后台 / 组件库文档的冷灰蓝
- ❌ 紫蓝渐变、AI 紫
- ❌ 毛玻璃
- ❌ 巨大营销 Hero + 无意义插画
- ❌ emoji 图标

## 技术边界

**不做：**
- 账号 / 数据库 / CMS
- AI API 调用（搜索和 Identify 全部本地规则）
- 付费系统
- 任何服务端

**要做：**
- 全静态（SSG）
- 每个词条独立 URL
- 完整键盘可达
- Reduced Motion 降级
- 移动端可用

## 隐私

- 学习进度只存 LocalStorage，**不联网**
- 无埋点、无分析脚本、无第三方字体
- 分享卡片在浏览器端 Canvas 生成，**图片不上传**
- 清浏览器数据 = 清空全部状态

## 已知取舍

| 取舍 | 决定 | 理由 |
| --- | --- | --- |
| 搜索用加权字符串匹配而非索引 | ✅ 接受 | 63 条数据，客户端全量扫描 <1ms，不需要索引 |
| Identify 用二维筛选而非 AI 理解 | ✅ 接受 | 零成本、零延迟、结果可解释；AI 反而会给出编造的词条 |
| 部分 Pattern 共用 Demo | ✅ 接受 | 如 `tooltip` 复用 IconButtonDemo、`card` 复用 ListDemo；先保证覆盖率 |
| 不做英文界面 | ✅ 接受 | 目标用户是中文独立开发者，英文术语本身就够用 |
| 不做社区评论 | ✅ 接受 | 需要审核成本和反垃圾，与「小而美」冲突 |
