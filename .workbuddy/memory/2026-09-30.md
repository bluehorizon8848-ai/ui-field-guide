## 静态导出 + Git 初始化

### 1. 开启 output: 'export'

`next.config.js` 改动：

```js
output: 'export',
images: { unoptimized: true },   // 原本就有，是 export 前置条件
trailingSlash: true,             // 新增，产出 patterns/modal/index.html 形式
```

`trailingSlash: true` 是为纯静态托管准备的：Cloudflare Pages 和 Nginx 都能直接命中目录形式，不需要 URL 重写规则。

**踩坑：Route Handler 必须显式声明静态。** 首次构建报错：

```
Error: export const dynamic = "force-static"/export const revalidate not configured
on route "/robots.txt" with "output: export".
```

修法：`src/app/robots.ts` 和 `src/app/sitemap.ts` 各加一行 `export const dynamic = 'force-static';`。

导出产物：187 文件 / 7.6 MB。

### 2. 本地静态预览服务器

`output: 'export'` 后 `next start` 直接失效，新增 `scripts/serve-export.mjs` + `npm run serve`。

**为什么不用 `python -m http.server`：**

| 行为 | python http.server | serve-export.mjs | Cloudflare Pages |
| --- | --- | --- | --- |
| 目录补尾斜杠 | 301 ✓ | 301 ✓ | 301 ✓ |
| 404 回退 404.html | ✗ 返回 Python 错误页 | ✓ 保留 404 状态码 | ✓ |

第一次用 Python 服务器跑，78 页里只有 404 页失败——因为它返回 500 字节英文错误页，被判成「body 几乎为空」。这是服务器问题不是产物问题（`out/404.html` 有 28 KB 完整内容）。

**中间踩的更隐蔽的坑**：先写了个内联 Python 404 handler，想给无尾斜杠路径补 301，结果判断条件写错，把 `/patterns/modal` 这类正常路径也判成不存在并返回 `404.html`（HTTP 200），78 页全挂。教训是**改 `SimpleHTTPRequestHandler` 行为时很容易破坏原生重定向**，最后老老实实写成独立 Node 脚本，显式处理 301 / 200 / 404 三种情况。

serve-export.mjs 还做了防目录穿越（`target.startsWith(ROOT)`）和缓存头区分（HTML no-cache / 资源 immutable）。

## Demo 展示区域加高 + 手机适配

用户反馈：Demo 展示区域高度太窄看不清，建议加大空间并适配手机。

### 诊断（先量测，不猜）

写了 `scripts/e2e/measure-demos.mjs`，遍历 63 个 Pattern 量 `.demo-stage` 实际宽高：

| 视口 | 舞台宽 | 舞台高 | 中位 | 矮于 200px |
| --- | --- | --- | --- | --- |
| 375px | 335 | 78~460 | 192 | **32 个** |
| 1440px | 796 | 94~476 | 208 | **30 个** |

最矮的只有 78px（`icon-button` / `tooltip`），84px（`badge`），86px（`modal` / `bottom-sheet`）。

**关键判断：这不是限高问题，是内容自然高度问题。** `DemoStage` 从没设过高度，是简单组件（一个按钮、一个小圆点）撑不起体量。

### 改法：统一最小高度

选了「统一 min-height」而非「按复杂度分级」——后者要给 63 个 Demo 逐个标注，工作量大且容易漏。

```tsx
// DemoStage.tsx
className={`demo-stage flex min-h-[240px] flex-col justify-center sm:min-h-[280px] ${pad ? 'p-5 sm:p-7' : ''} ${className}`}
```

手机 240px / 桌面 280px，配 `flex-col justify-center` 让内容垂直居中，不至于顶在上边。

改完：**240~460px，中位 240px，0 个矮于 200px**。

### 手机适配：6 处 flex nowrap 挤压

写了 `scripts/e2e/measure-crush.mjs` 排查。375px 下 6 个 Demo 有问题：

| Demo | 问题 | 修法 |
| --- | --- | --- |
| `navigation-rail` / `sidebar` | 60px 侧栏 + 内容区并排，窄屏挤 | 改 `flex-col sm:flex-row`，侧栏内部 `flex-row sm:flex-col` + `overflow-x-auto` |
| `icon-button` / `tooltip` | 7 个图标按钮 nowrap，最窄 1px | `flex-wrap` + 分隔线 `hidden sm:block` |
| `badge` | 3 个并排 gap-8 | `flex-wrap` |
| `context-menu` | 绝对定位按钮 + 文字 nowrap | 改 `flex-wrap` + `min-h-[220px]` + `p-4` |
| `popover` | `min-h-[180px]` 偏矮 | 提到 220px |

顺带把 `empty-state` / `error-state` 的 `min-h-[180px]` 也提了。

**没动的**：`ActionDemos.tsx:188` 的 `h-[240px]`（FAB 的页面滚动区模拟）和 `InteractionDemos.tsx:330` 的 `min-h-[150px]`（拖拽放置区）——这两个高度是**场景模拟的一部分**，不是 Demo 容器。

### 检测脚本的坑

第一版 `measure-crush.mjs` 误报了两类：

1. **`table` 报 27 处溢出 246px** —— 实际在 `.table-scroll`（`overflow-x-auto`）里，是合法横向滚动。加了 `inScrollable()` 祖先链检查排除。
2. **`sidebar` 在 768px+ 报挤压** —— 那是「60px 固定侧栏 + 主内容区」的刻意设计。排除条件：第一个子元素 `flex-shrink: 0` 且 class 带 `w-[` 且只有 2 个子元素。

最终 320 / 375 / 768 / 1440 四个视口全部 **0 / 63 有问题**。

### 视觉测试加第 6 项

把高度和挤压断言并入 `visual.mjs`（原 5 项 → 6 项），防止将来改样式时回退。`measure-demos.mjs` / `measure-crush.mjs` 保留为独立量测工具，不参与 e2e 判定（`npm run e2e:measure` / `e2e:crush`）。
