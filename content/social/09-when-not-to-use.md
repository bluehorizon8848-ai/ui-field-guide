# 09 · 我给 63 个 UI Pattern 写了「什么时候不要用」

> 首发第 9 篇 · 引入 When Not to Use

## 痛点

大部分设计教程只讲「这个组件怎么用」，不讲「什么时候别用」。

结果就是：所有页面都是 Dialog，因为 Dialog 最万能。

## 最有价值的一栏，是「不要用」

举例，Toast 的「什么时候不要用」：

```
- Toast 里放「撤销」按钮那就变成 Snackbar 了，别混用。
- 连续操作时会堆叠成一列 Toast，看起来像出了错。
```

**这两条比「Toast 出现 2-4 秒」有用一百倍。**

因为参数是描述，而「不要用」是判断。独立开发者缺的是判断。

## 我写的规则比我想的更狠

### Alert：不可逆或高后果

```
「这条规则唯一真正的场景是：后果不可逆或代价很高。」
```

删了 20 张照片，用 Snackbar 给了「撤销」，但用户手快关掉了 —— 这时候 Snackbar 是失败的，因为它假装给了选择。

### Segmented Control：不能当按钮组

```
「用 Segmented Control 的语义是『选项之一』，不是『动作』。
 动作是 Button 的活。」
```

### Tooltip：不能承载关键信息

移动端没有 hover。所有只在 tooltip 里的信息，等于不存在。

**这条应该是硬约束，但我写成了「强烈建议」。** 后来想，「强烈建议」这种词在实践中等于「随便」。

## 一个副产品：写「不要用」能逼你看清本质

写 Alert 的「什么时候不要用」时我发现，Alert 和 Modal 的区别不是「有没有遮罩」，而是**要不要用户做决定**。

Modal 是「我需要你输入点什么才能继续」。
Alert 是「我需要你承认一件事才能继续」。

这个区分在我写之前是模糊的。写完就清楚了。

**教一件事的最好方式，是逼自己回答「它不适用于什么」。**

## 怎么用这一栏

读到一个词条，别只看 Demo。直接跳到「什么时候不要用」。

如果你的场景正好命中其中一条 —— 恭喜，你避免了最常见的那种「技术上没错但体验很糟」的决定。

比如：

- 你要用 Modal 展示一条信息 → 停，可能应该是 Toast 或 Banner
- 你要用 Tooltip 放操作说明 → 停，移动端用户看不到
- 你要用 Spinner 做首屏加载 → 停，应该是 Skeleton
